# Ядро Plumix без Avalonia и рендер через Impeller

> PRD. Актуально на 2026-11-22. Статус: решения приняты; этапы 0–3
> выполнены, ядро без ссылок на Avalonia, SkiaSharp и HarfBuzzSharp; прототип
> на NImpeller (этап 4) проверен на Pixel 4a 5G — замеры, экраны NetBench и
> список пробелов C API готовы; дальше решение (этап 5).

---

## Зачем

После `1.0.0-preview.5` публичный API `Plumix`, `Plumix.Material` и
`Plumix.Cupertino` не называет типов Avalonia (см. `avalonia-free-api.md`).
Но сборка `Plumix` по-прежнему ссылается на пакеты `Avalonia`,
`Avalonia.Skia`, `SkiaSharp` и `HarfBuzzSharp` и использует их внутри.
Поэтому приложение на Android или iOS нельзя собрать без Avalonia, даже если
оно не трогает ни одного её типа.

Одновременно появился готовый кандидат на рендер для нативных хостов —
NImpeller: привязки .NET к C API Impeller, растеризатора Flutter. Их ведёт
команда Avalonia.

Этот документ описывает, как убрать Avalonia из ядра и как проверить
NImpeller на практике, не делая на него ставку заранее.

## Цель и границы

**Цель.**

1. Сборка `Plumix` не ссылается ни на `Avalonia*`, ни на `SkiaSharp`. Всё,
   что зависит от конкретного рендера и платформы, живёт за внутренними
   интерфейсами бэкенда; реализация на Avalonia и Skia находится в
   `Plumix.Avalonia`.
2. Есть работающий прототип: приложение Plumix на Android без Avalonia,
   рисующее через NImpeller. По его результатам принимается решение, делать
   ли нативный хост официальным.

**Не входит в этот PRD:**

- Официальный нативный хост для Android или iOS. Прототип не публикуется в
  NuGet.
- IME, accessibility, буфер обмена, системные диалоги в прототипе.
- Замена Avalonia на десктопе и в браузере. Там хост на Avalonia остаётся
  основным; у NImpeller нет сборки под WebAssembly.
- Изменения публичного API. Все этапы — внутренние.
- Собственный рендерер или переписывание Impeller на C#.

## Что сейчас внутри

Снято по исходникам `Plumix` на коммите `03ebee9e` (`v1.0.0-preview.5`).

Файлов с директивами `using` для Avalonia, SkiaSharp или HarfBuzzSharp:
85 из 602 в ядре, 17 из 193 в `Plumix.Material`, 12 из 63 в
`Plumix.Cupertino`. До работы над публичным API в ядре их было 312.

| Узел | Чем пользуется ядро | Файлов в ядре |
|---|---|---|
| Пути | `Geometry`, `StreamGeometry`, `SKPath` | 43 |
| Краска | `IBrush`, `IPen`, кисти градиентов | 43 |
| Растеризация | `DrawingContext`, `ICustomDrawOperation`, `SKCanvas`, доступ к Skia через Avalonia | 18 |
| Ввод | типы клавиш и указателей Avalonia | 14 |
| Картинки | `Bitmap`, `RenderTargetBitmap`, кодеки Skia | 10 |
| Цикл событий | `Dispatcher`, таймеры | 10 |
| Текст | форматтер, шейпер и менеджер шрифтов Avalonia | 9 |
| Шейдеры и фильтры | `SKShader`, `SKRuntimeEffect`, фильтры Skia | 6 |
| Матрицы | конверсия в `Matrix` Avalonia | 3 |
| Ресурсы | `AssetLoader` | 1 |

Один файл может попадать в несколько строк.

Главное препятствие — устройство `Canvas`. Он записывает команды как
замыкания над `DrawingContext` (`CanvasCommand` в `UI/Canvas.cs`), то есть
записанная картинка непрозрачна и проигрывается только в Avalonia.

Painter-ы `Plumix.Material` и `Plumix.Cupertino` вызывают внутренние
перегрузки `Canvas` с кистями, перьями и `Geometry` напрямую.

## Что такое NImpeller

Состояние на 2026-11-21, репозиторий `AvaloniaUI/NImpeller`.

- Привязки генерируются из `impeller.h`; лицензия MIT; совместимы с AOT.
- Пакеты в NuGet: `NImpeller` и нативные библиотеки для Windows, Linux,
  macOS, Android (arm, arm64, x64), iOS, tvOS, Mac Catalyst. Версия
  `3.50.0.1`, собрана из Flutter 3.50.0.
- Нативные библиотеки собираются из форка `AvaloniaUI/flutter` с патчами.
- В репозитории есть примеры минимальных хостов: Android на EGL и GLES,
  Apple на Metal.

Что покрывает C API форка (192 функции, в апстриме Flutter 3.47 — 176):

- построитель display list: фигуры, пути, клипы, слои, тени, трансформации;
- градиенты, фильтры цвета, размытия, фрагментные программы;
- текстуры из пикселей и из текстуры OpenGL;
- абзацы на текстовом стеке Flutter;
- поверхности поверх FBO OpenGL ES, drawable Metal и swapchain Vulkan.

Форк добавляет к апстриму три вещи: создание шрифта из байтов
(`ImpellerTypefaceNew`), рисование готовых глиф-ранов
(`ImpellerGlyphRunNew`, `DrawGlyphRun`) и параметры контекста.

Чего в C API нет:

- чтения пикселей обратно — нечем сделать `ToImage` и скриншоты;
- декодирования картинок;
- измерения путей и булевых операций над ними;
- `drawVertices` и `drawAtlas`;
- у абзацев — заполнителей под встроенные виджеты, прямоугольников
  выделения, межбуквенного интервала, strut и настроек шрифта.

Известные проблемы: Vulkan на Android в C SDK не работает (об этом сказано
в README проекта), остаётся GLES. Проект молодой: около 90 коммитов, один
основной автор, релизов на GitHub нет.

## Принятые решения

Приняты 2026-11-21. К каждому указана отвергнутая альтернатива.

1. **Картинка — это данные.** `Canvas` записывает список типизированных
   команд из своих типов (`Path`, `Paint`, `Shader`, `RasterImage`,
   абзац), а не замыкания. Бэкенд проигрывает этот список. Альтернативы
   нет: без этого ядро не отвязать ни от какого рендера.
2. **Бэкенд — набор внутренних интерфейсов, который регистрирует хост.**
   Растеризация, текст, картинки, геометрия путей, цикл событий и кадры,
   ресурсы. Публичным API это не становится; доступ — через
   `InternalsVisibleTo`, как сейчас у `Plumix.Avalonia`.
3. **Avalonia и Skia остаются эталонным бэкендом.** Существующий код
   переезжает в `Plumix.Avalonia` без изменения поведения. Пиксельный
   паритет с Flutter продолжает проверяться на нём.
4. **У ядра нет нативных зависимостей.** `SkiaSharp` и `HarfBuzzSharp`
   уходят в пакеты бэкендов. Альтернатива — оставить `HarfBuzzSharp` в
   ядре ради общего шейпинга; отвергается, потому что бэкенд на Avalonia
   шейпит её средствами.
5. **Текст на Impeller — свой layout и глиф-раны.** Шейпинг HarfBuzz,
   раскладка строк своим кодом, рисование через `DrawGlyphRun`.
   Альтернатива — абзацы Impeller: проще и ближе к Flutter, но без
   заполнителей и прямоугольников выделения на них не построить
   `EditableText` и встроенные виджеты.
6. **Геометрия путей — управляемый код в ядре.** Измерение длины, точки на
   пути, проверка попадания и булевы операции переносятся с `SKPath` на
   собственную реализацию. Альтернатива — служба бэкенда; отвергается,
   потому что у Impeller этих операций нет вовсе.
7. **Прототип — Android на GLES.** Vulkan не работает, а Android — платформа,
   где у Avalonia было больше всего проблем. Проверочное устройство —
   Pixel 4a 5G (API 34).
8. **Этапы 1–3 идут до `1.0`, прототип — независимо.** Убрать транзитивную
   зависимость от Avalonia из пакета `Plumix` после заморозки было бы
   заметным изменением для пользователей.

## Этапы

Этапы 0–3 — в репозитории `Plumix`, каждый оставляет сборку и тесты
зелёными. Этап 4 — отдельные неопубликованные проекты.

### 0. Счётчик зависимостей

Тест считает, сколько членов из сборок `Avalonia*`, `SkiaSharp` и
`HarfBuzzSharp` использует `Plumix.dll`, и не даёт числу расти.
`HostBinaryCompatibilityTests` уже перечисляет эти члены — счётчик строится
на том же обходе. Цель этапа 3 — ноль.

Сделано 2026-11-21: `HostDependencyBudgetTests` в `Plumix.Tests` считает
типы и члены по каждому пакету и падает и при росте, и при снижении (бюджет
опускают в том же изменении). Стартовые числа: ядро 704, `Plumix.Material`
31, `Plumix.Cupertino` 41.

### 1. Painter-ы Material и Cupertino

29 файлов переходят с внутренних перегрузок `Canvas` (кисти, перья,
`Geometry`) на публичные с `Paint` и `Path`. После этого внутренние
перегрузки удаляются.

Сделано 2026-11-21. Все 29 файлов рисуют через `Paint` и `Path`; бюджет
`Plumix.Material` и `Plumix.Cupertino` — ноль. Вместе с ними на `Paint`
перешли 29 файлов ядра, и внутренние перегрузки отрисовки с кистями,
перьями и `Geometry` удалены; осталось внутреннее отсечение по `Geometry`
(`ClipGeometry`, `ClipGeometryLayer`) — его снимает этап 2. Ядро — 684
ссылки. Для прогресс-индикатора добавлен публичный `Canvas.DrawArc` (метод
`drawArc` из `dart:ui`, которого не хватало). Пиксельные тесты паритета не
изменились; по пути поведение сдвинулось к Flutter в двух местах: анимированные
иконки заливаются по правилу non-zero, штрихи — с пределом miter 4.

### 2. Картинка как данные

- `CanvasCommand` становится типизированной командой.
- `Path` хранит собственные сегменты; измерение и булевы операции — свой
  код (решение 6).
- `Paint`, `Shader`, фильтры — данные без объектов Avalonia и Skia внутри.
- Растеризаторы (`PaintRasterizer`, `FilterLayerRasterizer`, тени)
  читают данные и остаются на Skia.

Это самый рискованный этап: он затрагивает узлы «Пути» и «Краска», по 43
файла каждый.

Этап делится на шаги, после каждого — полный прогон пиксельных тестов:

- **2a. Команды.** Сделано 2026-11-21. `Picture` хранит типизированные
  записи (`UI/CanvasOps.cs`: фигура с `Paint`, `drawPaint`, тень, картинка,
  тонкая линия, `save`/`saveLayer`/`restore`, трансформации, отсечения
  `Rect`/`RRect`/`Path`), а проигрывает их один класс `CanvasPlayback` на
  Avalonia и Skia. Объекты бэкенда (кисти, перья, геометрия, растры слоёв)
  строятся при первом проигрывании и кешируются в записи, поэтому повторное
  проигрывание ничего не аллоцирует. Непрозрачными для ядра остались три
  вида записей: абзацы, отсечение по `Geometry` и маска прозрачности; их
  снимает этап 3. `CanvasCall` (журнал вызовов для тестов) хранит `Paint`
  вместо кистей и перьев. Ядро — 681 ссылка.
- **2b. Геометрия `Path`.** Делится на четыре шага:
  - **2b-1. Данные и построение.** Сделано 2026-11-21. `Path` хранит то же,
    что `SkPath`: глаголы, точки во `float`, веса коник, индекс последнего
    `moveTo`, признак овала или скругления. Все методы построения (дуги,
    овалы, скругления с нормализацией радиусов как в `SkRRect`, SVG-дуги,
    многоугольники, `addPath`/`extendWithPath`, аффинные трансформации,
    `shift`) перенесены с той же арифметикой. `PathSkiaParityTests`
    сравнивает тысячи случайных путей со Skia: глаголы совпадают точно,
    числа — до нескольких ULP. Причина допуска: нативный Skia на arm64
    сливает умножение со сложением (FMA), так что и сам Skia отличается
    между платформами. Рисование получает `SKPath` из этих данных
    (кешируется по версии пути); овалы и скругления пересобираются через
    `addOval`/`addRRect` Skia, чтобы сохранить его быстрые пути отрисовки.
    Ядро — 661 ссылка.
  - **2b-2. `contains`.** Сделано 2026-11-21. Счёт витков по прямым,
    квадрикам, коникам и кубикам с разбиением на монотонные участки, точки на
    контуре и пары совпадающих касаний — как в `SkPath::contains`; нужная
    часть `SkGeometry` (корни, разбиения, касательные) в `PathGeometry`.
    Ответы совпадают со Skia на всех проверочных точках, включая вершины и
    общие рёбра.
  - **2b-3. Измерение.** Сделано 2026-11-21. `SkContourMeasure` целиком:
    разбиение контура с допуском 0,5, позиция и касательная по длине,
    `extractPath`. Длины контуров совпадают со Skia точно. Ядро — 652
    ссылки. Трансформация с перспективой осталась нативной: ей нужно
    отсечение кривых по плоскости w = 0 (`SkEdgeClipper`), это пойдёт вместе
    с булевыми операциями.
  - **2b-4.** Булевы операции (`SkPathOps`) и отсечение для перспективы —
    самый большой кусок: около 18 тысяч строк C++ в `src/pathops`.
    Используются в `AutomaticNotchedShape` и `OutlineInputBorder`.
    Исходники Skia ветки `chrome/m119` (той, что внутри SkiaSharp 3.119)
    взяты разреженным клоном в `~/Documents/skia`, ссылка
    `Plumix/skia-src`. Перенос построчный, слоями, в
    `src/Plumix/UI/PathOps/`: основа (допуски, точки, кривые, понижение
    порядка), пересечения (линия–кривая, кривая–кривая через `SkTSect`),
    граф (спаны, сегменты, углы, контуры, совпадения, витки), операции и
    сборка результата. Проверка — сравнение `Path.Combine` с нативным
    `SKPath.Op` на случайных парах путей.

    Сделано 2026-11-21: 39 файлов в `src/Plumix/UI/PathOps/`, около
    23 тысяч строк C#; правила переноса — в шапке `SkPathOpsTypes.cs`.
    `Path.Combine` идёт через этот код. Дифференциальный тест сравнивает
    все пять операций со Skia на прямоугольниках, овалах, скруглениях,
    многоугольниках и случайных кривых с обоими правилами заливки, на
    совпадающих рёбрах и пустых операндах: успех, тип заливки, глаголы и
    точки совпадают на всех парах (в разовом прогоне — около 10 тысяч
    операций). Ядро — 650 ссылок. Нативной осталась только трансформация
    пути с перспективой: ей нужно отсечение по плоскости w = 0
    (`SkPathPriv::PerspectiveClip`), это отдельный небольшой шаг.
- **2c. Краска как данные.** Сделано 2026-11-21. `Shader` — данные:
  `GradientShader` (вид, точки, цвета в extended sRGB, остановки, режим
  повтора, локальная матрица), фрагментный шейдер с параметрами и его
  записанный снимок, программа фрагментного шейдера (исходник и раскладка
  параметров). Кисть Avalonia с нативным `SKShader` строит и кеширует
  бэкенд `SkiaShaders`; он же компилирует программы, ошибки компиляции
  по-прежнему выбрасываются сразу. `ColorFilter` и `ImageFilter` уже были
  данными — из `ColorFilter` убрано неиспользуемое отображение режимов
  смешивания на Avalonia. Затухание текста (`TextOverflow.fade`) стало
  типизированной записью холста вместо кисти Avalonia. Число ссылок ядра
  не изменилось (650): код преобразования переехал из данных в
  `SkiaShaders`, но остался в той же сборке — уйдёт на этапе 3.

Итог этапа 2: `Picture`, `Path`, `Paint`, `Shader` и фильтры — данные
из типов Plumix. Непрозрачными для ядра остались абзацы текста и
отсечение по `Geometry` (оба — этап 3), а нативной — трансформация пути
с перспективой.

### 3. Интерфейсы бэкенда и переезд

- Интерфейсы: растеризация, текст и шрифты, кодеки картинок, цикл событий
  и кадры, ресурсы, клавиатурные коды.
- Реализации на Avalonia и Skia переезжают в `Plumix.Avalonia`.
- `Plumix.csproj` теряет ссылки на `Avalonia`, `Avalonia.Skia`, `SkiaSharp`,
  `HarfBuzzSharp`.
- Тестовый абзац (`HeadlessParagraph`) остаётся в ядре: он не зависит от
  платформы.

Этап делится на шаги; реализация на Avalonia переезжает в `Plumix.Avalonia`
сразу на своём шаге, а не в конце. Хост ставит реализации в статические
`Current` внутренних интерфейсов из инициализатора модуля
(`AvaloniaBackend`), тестовая сборка вызывает его первым. Без хоста ядро
бросает понятную ошибку.

- **3a. Мелкие использования.** Сделано 2026-11-21. Убраны `using`
  Avalonia, которые ничего не использовали; мёртвый код (`RotatedBox`,
  `BorderSide.ToPen`) удалён; `StarBorder` строит матрицу через `Matrix4`,
  как Dart. Удалено неиспользуемое отсечение по `Geometry` Avalonia
  (`PushClipGeometry`, `ClipGeometryLayer` и вся цепочка до проигрывателя).
- **3b. Поток UI и таймеры.** Сделано 2026-11-21. Внутренний
  `IPlatformThread`: `Post` с приоритетами микрозадачи/задачи/кадра,
  таймер, разовый отложенный вызов. Через него идут цикл событий, кадровые
  часы, таймер жестов, отчёт о таймингах и горячая перезагрузка.
  Реализация на диспетчере Avalonia и правка его часов — в
  `Plumix.Avalonia`.
- **3c. Клавиатура.** Сделано 2026-11-21. Карты клавиш хоста
  (`HostKeyboardMap`, `HostKeyEventMessage`) использовались только хостом и
  переехали в `Plumix.Avalonia`. Ядро — 620 ссылок.
- **3d. Картинки.** Сделано 2026-11-21. `RasterImage` — непрозрачный образ
  бэкенда с размером в пикселях и логическим размером, которые задаёт
  бэкенд. Декодирование (`InstantiateImageCodecWithSize`) и
  `Image.toByteData` идут через внутренний `IImageBackend`, ресурсы — через
  `IAssetSource`. Кодеки (растровый, многокадровый Skia, APNG), чтение
  пикселей и `AssetLoader` — в `Plumix.Avalonia`; PNG для инспектора
  берётся через `toByteData`. Ядро — 574 ссылки.
- **3e. Растеризация сцены.** Сделано 2026-11-21. Слои композитора в ядре
  — данные (дерево, свойства, сравнение сохранённых слоёв); рисование
  каждого слоя — в `FlowLayerPainter` и `SceneRasterizer` в
  `Plumix.Avalonia`, тела перенесены без изменений. `Scene.ToImageSync`
  идёт через внутренний `IRenderBackend`. Абзац отдаёт холсту
  типизированную запись (`DrawPictureOp` для текста на Avalonia) вместо
  замыкания над `DrawingContext`; `Picture.Playback` ушёл из ядра.

### 4. Прототип на NImpeller

- Проект бэкенда: проигрывание списка команд в display list Impeller,
  текстуры, градиенты, фильтры, фрагментные программы.
- Текст: шейпинг HarfBuzz, свой layout, глиф-раны (решение 5). Подбор
  системных шрифтов — по списку шрифтов Android.
- Минимальный хост по образцу `Sandbox.Android`: поверхность EGL, кадры по
  `Choreographer`, касания, жизненный цикл активити.
- Картинки декодирует платформа.
- Сценарии: экраны мобильной части NetBench и выборка страниц `Sample`.

Ход работ (ветка `proto/impeller` в `Plumix`):

- **4a. Каркас и первый кадр.** Сделано 2026-11-22. NImpeller собирается из
  HEAD (`nimpeller-src`): в NuGet `3.50.0.1` нет `ImpellerTypeface` и
  глиф-ранов. `src/Plumix.Impeller` проигрывает записи холста и дерево слоёв
  в display list (фигуры, пути с коническими кривыми через квадратичные,

  backdrop). `src/Sample/Plumix.Sample.Impeller.Android` — Activity с

  Демо (Material-список с градиентами и тенями, FAB) работает в эмуляторе
  Pixel 4a API 34: прокрутка и нажатия доходят. Текст пока рисуется

- **4c. Картинки.** Сделано 2026-11-22. Декодирует платформа

  сборку приложения сам (`PlatformAssetBundle.ApplicationAssemblyName`).

  потоке растеризации, тайминги кадров возвращаются в UI-поток. Реактор GLES

  завершением процесса и дали те же 1086 мс). В Release нет блокировки
  главного потока на 6–8 с, которая была в Debug.

  в эмуляторе. Заодно: имена системных семейств из `fonts.xml` (`monospace`,

### 5. Решение

По итогам прототипа — отдельный PRD на официальный нативный хост либо
запись, почему от него отказались.

Черновик решения — `native-host.md` (2026-11-22): три варианта,
рекомендация делать хост официальным с публикацией после релиза NImpeller с
нужным API и паритета платформы Android. Принято 2026-11-22: вариант 1,
NImpeller — пакет `Plumix.NImpeller` из своего форка.

## Критерии готовности

Этапы 0–3:

- `Plumix.dll` не ссылается на сборки `Avalonia*`, `SkiaSharp`,
  `HarfBuzzSharp`; счётчик равен нулю.
- Полный прогон `Plumix.Tests` зелёный; пиксельный паритет с Flutter не
  хуже, чем на `v1.0.0-preview.5`.
- Время кадра на бэкенде Avalonia не выросло заметно на существующих
  замерах: список команд не должен добавлять аллокаций на кадр.
- `Plumix.Packages` и `NetBench` собираются без изменений в своём коде.

Прототип (этап 4) считается успешным, если на Pixel 4a 5G:

- выбранные сценарии отображаются и отвечают на касания;
- расхождение с бэкендом Skia на тех же сценах описано постранично;
- время кадра и холодный старт не хуже текущего хоста на Avalonia;
- измерен размер APK в сравнении с текущим;
- составлен список пробелов C API с пометкой по каждому: обходится своим
  кодом, требует патча в форк или блокирует.

Итог на 2026-11-22: все пять пунктов выполнены (разделы 4e–4h). Время кадра
и тёплый старт лучше хоста на Avalonia, старт без кэша шейдеров драйвера — на
его уровне; APK меньше на 10,5 МБ; блокирующих пробелов для выбранных
сценариев нет. Расхождение со Skia описано по всем 163 страницам галереи
(4e), экраны NetBench сверены с магазинной сборкой (4g).

## Риски

- **Зрелость NImpeller.** Один основной автор, частые изменения, зависимость
  от форка Flutter. Смягчение: до этапа 5 NImpeller используется только в
  неопубликованном прототипе.
- **Регрессии паритета на этапе 2.** Перевод замыканий в данные меняет путь
  каждого примитива. Смягчение: этап делится по видам команд, после каждого
  — прогон пиксельных тестов.
- **Нет чтения пикселей в Impeller.** `ToImage`, скриншоты инспектора и
  прогрев шейдеров в прототипе не работают либо делаются через собственный
  FBO и чтение средствами GLES.
- **Свой текстовый стек.** Подбор системных шрифтов и сложные письменности —
  отдельная работа; в прототипе покрывается только латиница и кириллица.
- **Встречный риск со стороны Avalonia.** Ядро сейчас берёт Skia у Avalonia
  напрямую для шейдеров, теней и фильтров. Если Avalonia сменит рендер,
  этот путь перестанет работать. Этапы 2–3 снимают и этот риск: прямое
  обращение к Skia остаётся в одном пакете.

## Открытые вопросы

- **Имена пакетов.** `Plumix.Android` занят хостом на Avalonia. Имя для
  нативного хоста и для бэкенда на Impeller решается на этапе 5.
- **Чтение пикселей.** Предлагать ли патч в форк Avalonia или держать
  обходной путь у себя.
- **Шейдеры.** Impeller принимает фрагментные программы в своём формате,
  собранные `impellerc`; сейчас в `Plumix.Material` лежит `ink_sparkle` на
  SkSL. Нужен ли общий исходник и два результата сборки.
- **iOS.** Делать ли второй прототип на Metal до решения на этапе 5 или
  считать Android достаточным.
